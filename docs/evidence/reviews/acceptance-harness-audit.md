# Acceptance harness audit

Read-only review of `scripts/verification/` and the existing evidence. Line numbers refer to the scripts as reviewed. The browser paths drive the real UI and collect real server and Phaser state. The isolated benchmark provisions its disposable characters through HTTP and Prisma. No services or suites were run for this review.

## Fix before interpreting the long runs

1. **Performance failures can exit successfully, and the full-load test counts different populations.** `performance-fixture.mjs:78–90` logs `meetsFrameTarget` and `fullLoadEverySample` with no failure path when either is false. `browser-helpers.mjs:103–108` counts every visible entity sprite centered in the camera, independent of the live monster and boss IDs read from the server. The three aggregate counts therefore leave the required intersection unverified. Load samples occur only after every four movement pulses, about once per second. Join snapshot IDs to Phaser sprites and aggregate the ten living, combat-active normal actors and one living, combat-active boss present in the camera together. Require fresh snapshots, positive coverage over the measured interval and a living player, and fail explicitly when the workload or frame threshold misses. If retaining periodic samples, label the load claim with that cadence. `ATTACKING` at `performance-fixture.mjs:85` belongs to the player state vocabulary. The enemy state list is in `server/src/engine/realtime-arpg-engine.ts:112`.

2. **Post-render frame math is valid between callbacks but can hide lost coverage.** `browser-helpers.mjs:165–185` uses real post-render times and correctly computes average FPS as interval count divided by elapsed interval time. Dropping the initial partial interval is reasonable. The reported duration is only first-to-last callback time, so a stalled or paused tail is absent even if the outer loop waits 45 seconds (`performance-fixture.mjs:79–90`). Zero or one callback yields no intervals and a non-finite FPS. Record monotonic wall duration and start/end gaps separately, require sufficient finite intervals and window coverage, and use a documented percentile convention. `play-session.mjs:127–128` also accepts a missing probe as an `ok` result containing `null`, and a second `measure-start` leaves the first listener attached. Reject an unmatched stop or duplicate start.

3. **Four skill keys prove a cooldown transition only.** `performance-fixture.mjs:59–66` logs the advertised MP cost, MP delta and displacement without checking any of them. The final screenshot follows the fourth cast and supplies no per-cast effect evidence. A successful keypress with an incorrect cost or missing effect can still produce a successful fixture result. If used as functional evidence, bind the before/after authoritative tick to the specific cast, account for MP regeneration, and validate the claimed cost and outcome for that slot. Label a standalone result as a four-slot activation check until these checks are present.

4. **Bind reload and reconnect to a new socket's authoritative tick.** `browser-helpers.mjs:50–59,64–85` correctly scopes CDP request IDs to the document, but `webSocketCreated` counts an attempt before handshake and `latest` survives navigation and socket replacement. At `performance-fixture.mjs:67–72`, a newly created socket can satisfy the count while `latest.type` comes from the previous socket. `browser-smoke.mjs:29,101–109` and `play-session.mjs:125–126` also use a global latest state or a creation count. Track the emitting socket and document generation, then wait for a TICK from the replacement before checking controls or persistence. The fixture's actual `server.websocketServer.clients` inspection is the right socket-ownership source. If claiming the old descriptor was cleaned up, require `OPEN=1` and `CLOSING=0` or `total=1` at the settled check. The saved probe recorded `OPEN=1`, `CLOSING=0`, `total=1` at its observation point. Browser smoke evidence alone only speaks to the current document.

5. **Recorded command success can precede the claimed outcome.** `play-session.mjs:61–72` records a kill if the target disappears from the snapshot. Require authoritative death or correlated kill evidence, and fail if the map or target is lost before confirmation. At `:50–60`, reaching the dialogue loop cap returns normally. At `:108–120`, quest and equip commands return fresh API state without checking the intended transition. Fail unresolved commands or verify these postconditions before marking them `ok`. At `:165–177`, `finish` publishes success before context close, video finalization and manifest write, and the batch can still process commands queued after `finish`. Stop intake at `finish` and treat the finalized manifest and readable recording as completion evidence.

6. **Queue publishing has a reader race and a shorter budget than walking.** `play-session.mjs:169` writes the final path directly while `send-command.mjs:12–16` reads and parses immediately after it appears. Publish results through a temporary file and atomic rename, as the sender already does for requests. The sender stops polling at 120 seconds, while `walking-route.mjs:54–59` grants up to 40 seconds to each waypoint and can continue driving the UI after the sender times out. Provide a wait or resume path for the same command ID so a slow prior walk cannot be executed twice by a retry.

## Evidence and isolation

- **Panel and wall checks need direct action evidence.** `browser-smoke.mjs:68–72` presses dodge and skill keys but compares only the `ATTACK` counter, with no attack click in the panel. `:90–93` checks the wall position after Space without confirming a dodge, so a missed keypress also passes. Capture the action baselines and actual blocked inputs, and require a confirmed dodge for the wall check. The existing smoke result JSONs each carry an explicit failure. Their names and screenshots do not establish a complete smoke pass.
- **The existing focus result is correctly inconclusive.** `focus-probe.mjs:19–31` reports the real headless tab switch without observed focus loss. In a browser that exposes focus loss, `:23–26` supplies an explicit keyup before measuring stale movement, which can itself remove the stale state. Keep the original key held through focus recovery until after the stale-motion window. For any repeat, verify gameplay ticks continued while unfocused and verify foreground focus recovered before measuring fresh movement.
- **The high-realm setup is disclosed, and cleanup needs wider failure coverage.** `performance-fixture.mjs:18–21,40–48` requires a loopback `_test` database and identifies realm index 8/tier 3, the adjusted spawn layout, and the extra learned skills. Preserve that disclosure with per-run scope so `VANDAO_FIXTURE_SCOPE=network` evidence is identified as network-only. `:35–51,94–100` initializes services before `try`, and the sequential shutdown can skip account deletion and final evidence if an earlier close throws. Track invocation-owned accounts as soon as registration begins, start resource tracking before service initialization, and attempt each cleanup even if a sibling step fails. Smoke, recorded play and focus only check a loopback frontend and leave registered fixtures on the connected stack (`browser-smoke.mjs:12–13,44–52,119–123`, `play-session.mjs:13–14,140–148,173–178`, `focus-probe.mjs:8–9,15–16,34`). Their disposable-stack requirement in `README.md:3` remains important because a frontend address cannot identify its backing database.
- **Identify the source actually measured.** `performance-fixture.mjs:40`, `play-session.mjs:18` and `browser-smoke.mjs:121` record `git rev-parse HEAD`. The harness directory is untracked at review time. Run against a committed source state or include the source-tree status and a stable identifier for the harness and other changed files used by that run.
