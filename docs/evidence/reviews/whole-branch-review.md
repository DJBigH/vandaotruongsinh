## Important — fix before checkpoint integration

1. **Retire the previous slot's live authority when the active character changes.** `server/src/modules/character/routes.ts:137` and `:366` change the account's active slot. `server/src/modules/arpg/ws-handler.ts:170` binds by character ID and `:200` accepts subsequent input by that character's socket/session identity. A live session for slot A can continue after another client selects or creates slot B. Starting B's socket replaces only an existing B socket. A can continue receiving ticks and moving, and its kills can pay A at `server/src/engine/realtime-arpg-engine.ts:616` while account-scoped HTTP reads target B. The existing same-character replacement test and the ordinary single-window switch/reload test both pass without covering this sequence. Make slot activation revoke the former slot's authority, account for authentication already in flight, and let the replacement continue. Verify both switching and creating a slot with an earlier socket still present. Preserve saves and genuine earned progress at the handover.
2. **Apply shrine healing to the authoritative actor.** The M1 village and forest both provide shrines at `server/src/data/maps.ts:101` and `:249`. `server/src/modules/world/routes.ts:208` uses the character's previously read JSON stats, overwrites the whole value and reports full healing. The next TICK reads the live session's HP/MP. A wounded player can use the displayed shrine, see success and remain wounded. The stale whole-value write can also revert concurrently updated persisted stats. The old branch already had this split. The revised live world interaction and committed-resource handling still expose it in the sample area. Use the live authoritative effect and current maxima, serialize compatible database operations, and cover injured HP and MP, death, and the supported offline path.
3. **Make potion debit and live restoration produce one truthful outcome across death.** `server/src/modules/inventory/routes.ts:43` checks eligibility before the awaited debit. `server/src/engine/realtime-arpg-engine.ts:1178` calls the live effect after commit, while `:274` silently skips a dead actor. The simulation can kill the actor during those awaits. The player then loses one item and receives the ordinary success result with no restoration. An actor dead at request start and an ordinary database rollback are covered separately. Define one ordering for death and the committed use. A failed use must leave the item available, and a successful use must correspond to an actual accepted effect. Preserve no-revival and rollback behavior. Put the death at the transaction/commit boundary in a deterministic test. Do not refund or apply an effect to a different character.
4. **Preserve an already-settled boss's respawn and reward state through an unrelated player death.** `server/src/engine/realtime-arpg-engine.ts:718` resets every boss when the player revives in the same map generation. A previously killed and rewarded boss awaiting its own timer becomes alive early. The reset at `:670` clears its respawn timestamp and leaves its reward flag set. Only normal respawn clears that flag at `:836`. The next legitimate kill of the prematurely revived boss can therefore pay nothing at `:925`. Test a settled boss kill followed by player death to another enemy before the boss timer, then verify the normal boss respawn and subsequent reward eligibility. Preserve the separate same-tick mutual-death rule and the reset for a live boss after a failed attempt.
5. **Identify the actual game before declaring a service ready.** `desktop-launcher/src/main/process-supervisor.ts:635` accepts any 200/401 response to the backend probe and `:648` accepts any 200 at the frontend root. An unrelated local HTTP application on the configured port is marked external game at `:263` or `:386`. The Open Game control can consequently send the user to the wrong site. The watchdog uses the same probes. The current port-forwarding fixture responds generically and tests only the positive case. Validate the game identity using the existing `/api/health` response at `server/src/index.ts:75` and a small stable frontend marker. Test wrong services with otherwise successful statuses, actual identified services and their ownership. No native-Windows session is necessary to cover these HTTP decisions.
6. **Require a disposable database before the new write-bearing regression suite begins.** `server/src/tests/world-session-routes-test.ts:25` opens the normal application. Its setup creates and later deletes rows through the resolved application client from `:37`. Setting NODE_ENV to test alone does not select a separate database. A maintainer can inadvertently run the documented command against a normal configured installation. Fixture-specific row names and later cleanup still permit writes to that database. The related guard at `scripts/verification/evidence-utils.mjs:26` checks authority hostname and database suffix, but omits the effective-endpoint override check used at `desktop-launcher/src/main/setup-manager.ts:317`. Validate the actual selected target and refuse ambiguous endpoint overrides before database work, using synthetic configuration to exercise rejection. Keep the independently documented historical isolated runs as valid evidence.
7. **Suppress the localized owner password in launcher output.** A fresh development seed prints the owner password after the Vietnamese label “Mật khẩu” at `server/prisma/seed.ts:34`. The setup runner filters selected database/JWT values at `desktop-launcher/src/main/setup-manager.ts:490` and sends this line through the sanitizer to the renderer at `:588`. The password recognizer at `desktop-launcher/src/main/logger.ts:22` handles English/configuration fields, so the actual application-produced localized password survives. The same sanitizer would retain that field in historical/current logs supplied to the TXT/ZIP exporter. Ordinary setup child stdout follows a GUI IPC path and need not have been written to an export in the observed runs. Remove the credential from the source log and cover this known localized field in sanitization, using only synthetic marker text for GUI and export tests. No public evidence file is asserted here to contain private account credentials.
8. **Make a retried breakthrough target the same progression event.** `client/src/api/game.ts:25` submits an unqualified POST. `server/src/modules/character/routes.ts:236` locks and checks the current character, computes the next tier, then charges that tier at `:275`. After a lost response, a retry runs against the newly advanced state. A character with enough accumulated cultivation pays again and advances twice for one user intention. For example the authored first two costs are 100 and 300 at `server/src/data/game-content.ts:59`. The user's explicit retry requirement appears at `docs/specs/VNEXT_REQUEST.md:280`. Bind the action to the viewed character and expected starting stage, or use an equivalent stable request identity. Verify a retry after successful commit and sufficient remaining cultivation, plus a deliberate subsequent advancement. Preserve correct behavior across slot changes.

## Behaviors considered and declined to judge beyond the evidence

- **Hardware performance, physical focus transitions, audio, complete animation fidelity.** SwiftShader failed at both measured resolutions. The headless tab probe never produced the required physical focus loss. Clips have no audio stream. Side-leg movement, foot pivot stability across every frame, and the partly obscured revival remain open. The visual review, testable control reset and generated source sheets do not resolve those observations.
- **Full native launcher and packaging.** Windows Electron/IPC, actual process-tree termination/restart, WSL behavior, generated binary/icon and console launcher portability need their own target-environment verification. The inherited compiled server output/ESM start and console port-ownership gaps are parked for M4, consistent with the restricted checkpoint. The GUI HTTP identity issue in Important 5 is already decidable in source. The front-end Vite forwarding fixture demonstrates configured proxy ports, not every externally supplied Vite environment or installed package.
- **Broader security and infrastructure.** The ordinary CORS policy, authentication hardening, development bootstrap defaults and multi-process session coordination were not certified. The single-process implementation and per-character queues provide the analyzed guarantees. The recorded security suite and bounded public-artifact scan cover their named assertions and patterns. No private environment, account state, external service or attack reproduction was used. Final archive/link checks belong to the controller's packaging step.
- **Reward recovery and save semantics outside the recorded loop.** A failed kill-reward transaction suppresses success notification. Recovery of a failed settlement across a process crash or restart has no demonstrated durable retry. Boss rematches are supported and must be distinguished from duplicate settlement of one defeat. Resource values after a backend restart, retained inactive sessions at scale and interrupted network requests other than the specific findings have no end-to-end recovery evidence. Four skills were verified on a prepared character. Natural later skill selection/order with more than four equipped records, retroactive unlocks and resource requirements of later realms remain progression work. No change to authored costs or balance is justified by these observations.
- **Travel and collision design beyond the first area.** The map panel deliberately exposes global travel to discovered entries and currently lists all maps. Portals and panel travel reuse server-selected destination spawns. I have not treated the absence of portal proximity on the general travel endpoint as an authorization defect without a different agreed fast-travel contract. The server's 300 px object-interaction tolerance exceeds the client's 90 px prompt. The source establishes that difference, but leaves the intended grace radius unspecified. Monster navigation through blockers, projectile hits versus walls within the same substep, and melee/AOE line-of-sight semantics need explicit authored behavior or representative encounters before declaring acceptance. The present shared sweep covers player movement and straight projectile blockers.
- **Other modes and provenance.** No completion finding for M2–M4 campaigns, other classes' original animation sets, turn-based combat, later maps, economy balance, admin, crafting, offline progression, or the full content catalog. The counts are registry counts. Independent evidence covers sampled runtime footage, not every raw frame, every secret encoding or third-party authorship beyond the recorded original-art production trail. The historical backend restart stamp does not attest loaded code from the running server. No new performance, gameplay or packaging result was inferred for later commits.
- **Scope of follow-up.** Each Important finding identifies its own regression case. Further hardware/visual work can proceed separately. Any post-review fix commit needs its own source identity, targeted regression results and review of the affected paths. The old clips and figures retain their original source identities.
