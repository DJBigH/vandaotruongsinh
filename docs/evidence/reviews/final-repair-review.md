## Remaining Important issue

**A retired window can displace the new slot's window.** At `server/src/modules/arpg/ws-handler.ts:40`, retirement closes the socket with code 1000 and the reason “Active character changed”. The scene's connection handles every close by invoking the retry scheduler at `client/src/game/exploration/connection.ts:42`. The fresh connection attempts AUTH after three seconds, or when the old tab next gains focus. The request at `client/src/game/scenes/ExplorationScene.ts:243` omits its character ID. The backend consequently binds it to the account's *new* active slot, then ejects the existing connection for that slot at `server/src/modules/arpg/ws-handler.ts:152`. The old window can now drive the new character. The server's single-owner count remains one throughout the final state, so that count alone cannot detect the wrong owner.

I instantiated the tracked `ExplorationConnection` in Node 24 using an in-memory socket factory and explicit timer callback. Feeding it the exact new code, reason and clean-close flag scheduled a retry. Running that callback created a second transport. This was a source-backed unit probe without network traffic, filesystem writes or private input. The first attempt used Node strip-only mode, which cannot parse the existing TypeScript constructor parameter property. Running the identical check with Node's TypeScript transform support succeeded. The subsequent AUTH and displacement follow directly from the two code paths above. The passing server tests at `server/src/tests/world-session-routes-test.ts:669` observe a retired bare WebSocket and deliberately connect the replacement by ID, so they do not exercise the old scene's retry timer.

Give slot retirement a terminal meaning for the displaced scene. Bind ordinary reconnect attempts to the character loaded for that scene, including after transport loss where no terminal reason reaches the browser. Verify that a retired window, including one returning to focus, cannot displace the new owner. Keep genuine transient reconnect for the same active character working. A focused two-window or equivalent combined client/server transport check should follow the retry interval and assert that TICK messages continue on the replacement.
