# Launcher startup contract review

Read-only audit on `codex/vnext-m1`. Existing build artifacts and baseline test evidence were inspected. A Node 24 check confirmed the entrypoint paths, emitted import shape, and literal dotenv placeholders. No services, builds, setup commands, database commands, or Windows GUI checks were run for this review.

## M1 default development path

- **Backend and setup use different environment sources.** Electron starts `npm run dev` in `server/` (`desktop-launcher/src/main/process-supervisor.ts:283–313`), as does the console launcher (`launcher.mjs:142–149`). Backend dotenv loads only repository `.env` from source and validates only presence (`server/src/config.ts:9–10,30–36`). Setup looks only for `server/.env`, creates it from a template, and overwrites it during forced dependency reinstall (`setup-manager.ts:84–85,213–252`). This is covered by the brief at line 8. Select the first existing file in `.env`, `server/.env` order, overlay explicit process variables, and use the same resolved values for setup inspection and children. An invalid selected file needs a clear diagnostic. Preserve either existing file during reinstall. Update the visible `server/.env` label in `TabSetup.tsx:259–265` if the inspection can now report a root file or process environment.
- **Prisma setup must receive the same URL.** Node's installed dotenv leaves `${DB_*}` in `DATABASE_URL` from both examples (`.env.example:2–7`, `server/.env.example:2–7`). Setup spawns in `server/` and forwards inherited values only (`setup-manager.ts:332–371,508–538`), while Prisma consumes `env("DATABASE_URL")` (`server/prisma/schema.prisma:9–11`). Pass the resolved URL in the child environment for Prisma generation, push, and seed. Existing seed and admin scripts instantiate Prisma independently (`server/prisma/seed.ts:5–14`, `server/src/scripts/create-admin.ts:5–9`, `server/src/scripts/set-admin.ts:1–4`), so direct documented CLI commands also require the right environment. Cover the launcher child path now as required by brief lines 8–9. If direct root-only CLI support is included, reuse a configuration loader without requiring a JWT for DB-only commands, or document how to supply their environment. Keep concrete URLs unchanged. If expanding component credentials, URI-encode substitutions and preserve existing URI options. The example DB password and Docker Compose's fallback differ when there is no root `.env` (`docker-compose.yml:9–13`). Align fresh development defaults with the documented Compose credentials without changing existing files or existing database credentials.
- **Inspection can report ready after real setup failures.** Prisma generation exceptions are caught, installation of `@prisma/client` is counted as generation, and the ready predicate omits npm and Prisma (`setup-manager.ts:107–130,332–339`). Failed schema push becomes a warning and arbitrary seed errors are treated as possible preexisting data (`setup-manager.ts:361–385`). Final verification can still print 100%, return success, and broadcast completed without an error (`setup-manager.ts:391–415`). The renderer uses `!payload.hasError` for its ready-to-play card and ignores `isReadyToPlay` (`TabSetup.tsx:59–67,379–409`). Preserve completion with warnings when DB synchronization was intentionally skipped or the TCP probe is unavailable, but gate readiness on usable configuration, required dependencies, and requested setup steps. Keep TCP reachability distinct from database authentication or schema readiness. Brief lines 6–9 address trustworthy tests and rejected placeholders, but do not explicitly cover these product/UI success paths.
- **Windows source checkout can fail before Electron opens.** The documented `CHAY_LAUNCHER.bat` source fallback calls npm install correctly, then runs bare `npm run build:main` followed by `npm run start` (`CHAY_LAUNCHER.bat:17–27`). The usual Windows `npm.cmd` requires `call` for control to return to the parent batch. A clean tree also needs the renderer build because Electron loads `dist/renderer/index.html` without a dev URL (`desktop-launcher/src/main/index.ts:105–110`). Build both targets with `call npm run build`, stop on failure, and invoke start with `call`. Root `launcher:dev` also builds main alone (`package.json:9`) and needs either a full build or an explicitly running renderer. Packaged EXE branches precede the fallback. These are outside current file ownership in the brief. Verify on Windows from a source checkout without `dist`; Linux build output cannot validate this branch.

## Adjacent startup issues

- **Optional Electron ports are inconsistent.** Launcher port settings drive readiness and Vite's listening port, but backend spawn sets `PORT` and `HOST`; Fastify config reads `SERVER_PORT` and `SERVER_HOST` (`process-supervisor.ts:250–255,290–313,405–424`; `server/src/config.ts:13–16`). The client Vite proxy sends `/api` and `/ws` to hard-coded port 3001 (`client/vite.config.ts:12–24`). A narrow follow-up can pass the chosen `SERVER_PORT` to both children, set `SERVER_HOST` to the supervisor's loopback bind, and derive both Vite targets from that port with the existing default. Test a non-default backend port, a successful proxied API response and WebSocket upgrade, and unrelated occupied-port handling without killing the listener. Setup's database TCP check also uses launcher `dbHost`/`dbPort` independently of the selected URL (`setup-manager.ts:87–103,341–349`). A custom URL endpoint should drive setup's probe or produce an explicit mismatch. The brief preserves defaults but does not cover custom settings.
- **Root `npm start` is the console launcher.** It directly spawns `cmd.exe` for both children even on POSIX (`package.json:7–8`; `launcher.mjs:142–149,177–184`). On Windows the console path still opens the browser and prints ready after readiness timeouts (`launcher.mjs:288–329`), and `freePort` force-kills the process listening on the configured port regardless of ownership (`launcher.mjs:49–68,242–244,276–278`). Treat console portability and ownership as separate from Electron's M1 path. The manual two-service `npm run dev` route is cross-platform.

## M4 production gap

`server/package.json:7–9` builds with `tsc` and starts `node dist/index.js`, but the actual output exists at `server/dist/server/src/index.js`. Even a start path edit leaves extensionless ESM imports (`server/dist/server/src/index.js:10–25`) and unresolved `@shared` aliases (`server/tsconfig.json:4–5,15–20`; `server/dist/server/src/engine/realtime-arpg-engine.js:5–6`). Node 24 rejected the bare `@shared` specifier. The existing config's `../../.env` also resolves to `server/dist/.env` from the emitted module. These are a compiled-runtime contract gap. The Electron and console launchers use source development commands, so a server build pass and M1 launcher pass do not establish that production `npm start` works. Track a build-to-start health smoke at M4; keep backend packaging outside Task 4.

## Focused verification additions

- Core test explicitly exits 0 after setting `process.exitCode = 1` and hardcodes its 100% label (`launcher-core-test.ts:25–32,168–187`). Encoding test repeats the pattern (`vietnamese-encoding-test.ts:24–30,183–190`). Setup script already exits 1 for failed assertions (`auto-setup-test.ts:90–98`), but assertions depend on real checkout `server/.env` and the alleged lock test only checks that cancellation is a function (`auto-setup-test.ts:46–88`). Baseline evidence is core 33/34 exit 0, setup 3/5 exit 1, encoding 30/30 exit 0. Verify a deliberate failed assertion propagates to a nonzero exit in each runner and successful totals are accurate. Isolate app-data and root folders; use injected command/probe fixtures for setup failures and the real concurrent-call path. The brief covers fixture isolation and the core runner; extend the runner fix to encoding and exercise the lock behavior.
- Minimum contract matrix: root-only, server-only, both files with differing values, explicit environment override, unresolved/missing required values, a punctuation-heavy concrete URL, and force reinstall retaining both file contents. Assert that setup invokes seed and Prisma with the same resolved URL that Fastify receives. Use a local TCP fixture for probe-only tests, then separately verify authenticated HTTP/gameplay against the existing isolated PostgreSQL integration environment. Add a requested-sync failure fixture so completed-with-warning cannot render a ready-to-play card.
